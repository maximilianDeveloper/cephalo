## [1.2.0] — unreleased

### Added

- **`scripts/build_reference_docx.py`** — builds the reference document from which Pandoc takes the layout of the exported DOCX (`--reference-doc`), from the values in `styleguide.md`: font, size, line spacing, paragraph spacing, alignment and first-line indent of the text; size, weight and colour of the headings, on every level; indent, size and spacing of block quotes; font, size and spacing of footnotes; the reference list's hanging indent; link colour; page size, margins, the page number and the title page's numbering. It starts from Pandoc's own reference document, or from a DOCX or DOTX template given with `--base`, adds the styles Pandoc uses where the starting document lacks them, replaces the template's own page number, and removes the theme fonts and colours that would win over a set value. In the second long-form trial run the Phase B orchestrator wrote a throwaway script for this and needed three corrections; the orchestrators now build the document with this script, and build it again with the corrected value after a layout finding. CI checks the result, and with Pandoc installed a round trip through it.

### Changed

- **After a third long-form trial run on Windows** — the run repeated the long-form trial with 1.1.2 and the new script (four chats, the student played by a second model, Phase B on Sonnet). Nine of the thirteen points its evaluation re-checked worked as intended: the reference document was built with the script from all 18 styleguide values, and the first format round found no layout error (the second run: four); title page, table of contents field, `Bibliography` style, one export per round, `py` and exit codes, nothing outside the project. The rest, and the run's new findings, came again mostly from the Phase B chat on the fast model:
  - **The format-verifier writes its own report** — the Phase B orchestrator saved the second format report shortened from 215 to 125 lines, the per-rule findings dropped, although the definition says to save it as it is. The format-verifier now has the Write tool and writes its report itself to the file the task prompt names, and writes no other file; the orchestrators read the file instead of copying the answer.
  - **Status in Phase B** — the Phase B orchestrator wrote no line to `00_Status.md` after either format round, only at the end, and left "Last handover" and "Next planned task" on the previous chat and the tasks it had finished; the pre-check result got no dated line for the styleguide questions it answered. The Phase B duties now give a format round as steps, with the status line as one of them, and the closure step names "Current focus" and the dated line below the pre-check result.
  - **The whole "does not occur" value** — the Phase B chat closed nine styleguide keys as "does not occur in this work" without "reopen if it occurs": the style-resolver definition gives the full value, the orchestrators named only its first half. They now give the whole string.
  - **Who writes the reference list** — without citekeys no definition said where the reference list comes from: in the second run the writer put one into the chapter file, in the third the Phase B orchestrator composed `bibliography.md` from `literature.bib` with nothing to check it against. `docs/reference_management.md` now says ("The reference list"): a file of its own, the last of every export, written by the orchestrator at the start of Phase B from the sources whose extracts name a chapter under **Used in**, with the checked bibliographic data and the styleguide's patterns; `bibliography_check.py` and the format-verifier check it. Chapter files carry no reference list; the workflows' export steps name the file.
  - **Which models are fast** — the Phase B chat on Sonnet reported itself as "not explicitly a fast model": no definition named one. `docs/phase_separation.md` and the status check now do (Sonnet and Haiku; a capable model such as Opus for Phase A).
  - **What the loop count leaves out** — the user's request for a new structure counted as an iteration of the chapter's feedback loop, as a polish round does. A change the user asks for that no finding prompted (a new structure, a section added, moved or removed; in the defense, a new slide order) no longer counts; the new verification after it runs all the same. Polish rounds still count.
  - **Waiting for the answer** — orchestrators asked the user and went on in the same turn, before the answer came. All three now end their turn with the question when what comes next depends on the answer; work the answer does not touch may come first.

## [1.1.0] — 2026-10-03

**Verbatim runs counted, quote IDs.** `scripts/verbatim_check.py` counts the verbatim word runs a chapter shares with its sources, and the orchestrators run it before every chapter verification, so that the source-verifier rates runs from a count instead of by eye. Each extract entry gets a stable quote ID, which the writer-agent's **Used in:** lines, the source-verifier's reports and the script point at. A third trial run on Windows tested both in the bachelor workflow, and a self-test of the script passed on Windows and macOS. The trial run's findings shortened the source-verifier's reports, set when a chapter passes, and grouped the style-resolver's open questions.

### Added

- **`scripts/verbatim_check.py`** — counts the verbatim word runs a chapter (`.md`, `.txt` or `.docx`) shares with its sources and rates them by the thresholds of `checklists/plagiarism_protection.md` (5–7 words 🟡, 8–14 ⚠️, 15 or more ❌). Sources are the quotes of the research-agent's extracts (with page and quote ID), the source registry in a seminar paper's `workspace/state.md`, PDFs and text files; it unpacks nothing and lists what it cannot read as not checked. A run counts across sentence boundaries and across citations (Pandoc citekeys, and author-year citations in parentheses); text in quotation marks, Markdown block quotes and Word quote-style paragraphs (also Pandoc's "Block Text") is left out as a marked direct quote. Each such quote is looked up in the sources instead, and one not found verbatim is listed for a check by hand. The words of a quotation shorter than five words keep a run going without being counted in its length, so that a term in quotation marks does not cut a copied sentence into pieces. A chapter's bibliography is not counted (the section under its heading, if every entry has a year; an appendix after it counts), and in PDFs the running headers, footers and page numbers are dropped, so that a run (and a word hyphenated at the page end) goes on across the page break. Exit 0 = no run of 8 or more words, 1 = at least one, 2 = bad arguments, an unreadable file, or no source text to compare against. The word index is built from the chapter, so book-length sources take little memory (about 50 MB for a million source words over several files). In both Windows trial runs, the writer-agent and the source-verifier counted verbatim runs by eye: the writer reported none of five or more words where a count found runs of five to seven, and a seven-word run across a sentence boundary went unreported. Documented in `docs/scripts.md`; CI runs it on generated Markdown, Word and PDF files.
- **Quote IDs in extracts** — each entry of a research-agent extract starts with a `### Q<n>` heading, numbered through the file and never changed or reused. The writer-agent's **Used in:** line (`Chapter 3 (Q1, Q4)`), the source-verifier's reports and `verbatim_check.py` now point at a single quote, not at a page that may hold several. Extracts without IDs stay valid and get them at their next edit; a missing or duplicate ID is a note under the extract verdict, not an error. A deleted entry keeps its heading (`### Q5 (deleted)`), so that its number is not given out again.

### Changed

- **Verbatim runs are counted, not estimated** — the orchestrators run `scripts/verbatim_check.py` on a chapter before every sentence-by-sentence verification and hand its report (`<name>_round_<n>_verbatim.txt`, beside the verification reports) to the source-verifier. Its step 8 rates the runs from that report, still judges by reading the paraphrases that only swap single words, and counts by eye only when no report comes. Workflow step A.4 of the bachelor and master workflows names the script, as does the long-form chapter chain; the seminar and presentation workflows tell the user to run it. A run of 8–14 words now gets immediate feedback to the writer like one of 15 or more, since both must be reformulated, and the status table lists a run of 15 or more words under ❌. The writer-agent no longer reports a count of its own as a check result. The orchestrators save the report with its error lines (`> <file> 2>&1`), create the `verification/` folder first, treat exit code 1 as a finished report, and hand the report on unrated; a rollback from Phase B runs the script before the passage is verified again. They check that the file is a report and tell the user when it lists PDFs as unchecked for want of `pypdf` or a source folder as not found. The source-verifier counts by eye for the sentences whose source the report did not compare, and its immediate feedback on a verbatim run names the run and the paraphrasing tier. The master workflow's methods chapter (A.M.2) gets the same check as A.4.
- **After a trial run of 1.1 on Windows** — a third trial run (Windows 11, Python 3.14) went through the bachelor workflow with the new features: the source-verifier found five of five planted errors, among them a 14-word verbatim copy the script rated ⚠️, flagged no correctly marked quote, and every extract entry had its quote ID. Its findings changed:
  - **source-verifier** — compact reports: one table row per ✅ sentence, full entries for the others, totals counted from them, and one format for extract checks. A chapter report had run to about 4,500 words, which the orchestrator had to retype to save it. Files are named by project-relative path (absolute paths carried the user's name into saved reports); quote IDs missing from the extracts' **Used in:** lines are listed as notes; a cited source the project does not have at all is ❌, not ❓.
  - **Orchestrators** — reports are saved as they come, status counts taken from their entries. A chapter passes when no ⚠️, ❌ or ❓ is left; 🟡 does not start a revision of its own, and the verifier's Used-in notes go to the writer as an edit of those lines only. The flat A → B criteria count ❌ and ❓ and compare the number of sources with the workflow's range. Chapter length is counted with `wc -w` instead of the writer's estimate (630 estimated, 752 counted). The flat state file gets the pre-check result section.
  - **research-agent** — names the range heading for a passage across pages, the two extra fields its rules use, and the language of its own text; **writer-agent** reports a length as an estimate; **pre-check** names `py` for Windows.
- **Shorter list of open style questions** — the style-resolver keeps contradictory or unclear rules (one entry each, with the readings) apart from rules the guidelines do not cover at all, which it groups into one entry per section and tag. In the trial run on Windows, a three-page guideline had produced 32 open questions, one per template key without a rule. An answer the user gives as provisional is recorded as `[provisional, user, date]` and stays on the open issues until confirmed.
- **Quotes the script can find** — the writer-agent marks block quotes with `>` (the script counts them as direct quotes, and Pandoc exports them as block quotes) and, in the seminar and presentation workflows, records its original quotes in the state file's source registry table, whose format only the orchestrator's definition gave. The methods-agent writes its extracts of methodological sources in the research-agent's form, with quote IDs, and fills their **Used in:** line.

## [1.0.1] — 2026-10-02

**First agent trial runs.** Two trial runs on Windows with fictional material, the second through the whole bachelor workflow, tested the agents in real work for the first time; a review of the trial set-up on macOS added one more point. Their findings tightened the agent definitions: how answers to open questions are recorded, when an extract counts as verified, when citations are written as citekeys, and how the orchestrators keep state and reports. Also new: a setup guide with screenshots, fixes in `bibliography_check.py` and both setup scripts.

### Added

- **`templates/styleguide.md`** — slots for common citation rules that had none: several sources in one citation, two authors, same author and year, sources without date or page numbers, secondary citations (`in_text.*`), the entry pattern per source type, co-authors and whether the original of a secondary citation is listed (`bibliography.*`), and the block-quote layout and how quotes may be altered (`style.*`). The format-verifier checks them, and the style-resolver tags `style.quote_alterations` `[content]`. In a Windows trial run the style-resolver had to invent 17 key names for rules of a three-page guideline, which the format-verifier's checklist did not know.

### Changed

- **style-resolver** — names its ways to read real guideline PDFs: the texts in `_styleguide_rawtext/` when the user has run `scripts/extract_styleguide.sh` (as `docs/scripts.md` and the script's closing message suggest, though the definition never mentioned the folder), otherwise the Read tool, and no extraction code of its own. In a Windows trial run it wrote its own `pypdf` one-liners instead, whose console output garbled umlauts and dashes.
- **Open questions in `styleguide.md`** — a defined way to record the user's answers (`style-resolver.md`, "Recording answers to open questions", referenced from all three orchestrators and `checklists/precheck.md`): the answer becomes the rule's value with its provenance, the entry moves to a new "Resolved questions" section of `templates/styleguide.md`, a partial answer leaves a narrower entry open, and "does not occur in this work" closes the entries for tables, figures or statistics a work will not contain. The orchestrators record answers themselves instead of running the style-resolver again. Before, no definition said how; in a Windows trial run each round of answers cost a new style-resolver run, and ten blocking questions, eight of them on rules a literature review without figures never needs, took two rounds before the first extract.
- **style-resolver** — an open rule has `❓` as its value wherever it appears; one of its competing readings must not stand as a value in another rule. In a Windows trial run the block-quote rule read "from 40 words" while the threshold itself was marked contradictory.
- **Extract verification** — the source-verifier's verdict on an extract covers its quotes, page numbers, term lists, secondary-citation flags and bibliographic data; remarks on the extract's own wording (core claims, labels) come as notes with the ✅ and are applied once by the research-agent, without a new round. Only a ✅ sets `verified`; an extract that reaches the loop limit without one stays `draft`, and the orchestrator asks the user. In a Windows trial run, 47 of 47 quotes and page numbers were correct on the first pass, yet seven wording notes started three more rounds (five agent runs, more than half of the session's cost), and the last extract was set to `verified` without a final ✅.
- **Orchestrators** — record each returned agent call in the state file (`workspace/state.md`, long-form `00_Status.md`) before the next call, not only at the end of a chapter or chat; the flat orchestrator also creates `workspace/state.md` at Step 0, which setup does not. In a Windows trial run the session ended at a usage limit with three new extracts the state file did not know.
- **Orchestrators** — two new principles: a task prompt names the definition, `styleguide.md` or checklist that holds a rule instead of paraphrasing it, and nothing is written outside the project folder, scratch copies included. In a Windows trial run the orchestrator's paraphrase assigned citation notation to `[content]`, against the style-resolver's own rule, and it left three copies of the extracts in the system's temporary folder.
- **`checklists/precheck.md`** — inspecting a file in the pre-check means `file` and a look at its first page; the research-agent and the style-resolver read sources and guidelines in full later. In a Windows trial run the orchestrator read every PDF in full during the pre-check, on the session's main model.
- **Citekeys only where they can be rendered** — the writer-agent writes Pandoc citekeys only when the decision log says the project renders them (a `literature.bib` plus Pandoc and a CSL file that matches the styleguide's citation style; a new item in section 6 of `checklists/precheck.md`), otherwise citations in the styleguide's format. It also gets the citekey forms for a prefix such as `vgl.`, a German locator and a secondary citation; `docs/reference_management.md` describes the case without a matching CSL file. Before, a `literature.bib` alone switched to citekeys: in a Windows trial run without Pandoc and without a CSL for the guideline, the chapter never showed a citation in the styleguide's form.

In a Windows trial run a planted synonym from that list was found but rated as mild as a stylistic "therefore".

- **ZIP extraction is routed through `scripts/extract_styleguide.sh`** in `research-agent.md` and `style-resolver.md`. Both previously instructed a bare `unzip`, bypassing the script's `safe_extract_zip()`, which rejects entries carrying absolute paths or `..` components. A prepared archive — a style guide downloaded from anywhere — could otherwise have written outside the target directory. The agents and `checklists/precheck.md` now also rule out every other extractor (`tar`, `7z`, Python `zipfile`, PowerShell `Expand-Archive`), the research-agent runs the script on a scratch folder with an explicit output folder, and CI guards against a regression.
- **Prompt-injection guardrails** added to all ten agent definitions: source and guideline content is material to quote and summarize, never a directive, and the same holds for the extracts, data files, handovers and agent reports the other agents read. Text inside a PDF, ZIP, or e-book can be written to read like an instruction addressed to the agent; the agents now record such text as a flagged note and continue the original task instead of acting on it. `style-resolver.md` lists it as a labelled "not a rule" open question, never in a rule section of `styleguide.md`; `source-verifier.md` labels it as instruction-like content rather than a citation issue. `SECURITY.md` names this risk, but no agent definition had previously addressed it.
- **`requirements.txt` gained upper bounds** (`python-docx>=1.0.0,<2.0`, `pypdf[crypto]>=6.0.0,<7.0`). An open range would silently pull in a new major release that changes the APIs these scripts rely on. The pypdf floor is 6.0, which caps decompressed stream size: with an older pypdf already installed, pip kept it, and a crafted guideline PDF could exhaust memory.
- **`docs/setup-wizard.html`: PowerShell quoting** — the generated command now also doubles the typographic single quotes U+2018–U+201B, which PowerShell treats as quote characters. A target containing one could end the quoted path and run the rest of the field as PowerShell commands; an ordinary folder name with an autocorrected apostrophe (`O’Brien`) broke the command.

- **`extract_styleguide.sh` caps disguised ZIPs** at 512 MiB unpacked and 10,000 entries ("Blocked (security)"), so a small crafted archive can no longer unpack to more than that (a text member close to the cap is still read into memory whole, which takes several GiB).
- **Personal data in generated projects** — `.gitignore` (and the copy both setup scripts write) now keeps all of `data/raw/` and `data/processed/` out of Git, as the workflows promise, instead of only `*.csv`/`*.xlsx` and `*_personal*`/`*_identified*` names (interview transcripts or SPSS files could be committed); the `data/processed/.gitkeep` placeholder is now actually committed, in multi-project main works too. ## [6.2.0] — 2026-04-22

First genuine feature release after the v3→v6.1 hardening series. Users can now choose where their project lives, instead of being forced to work inside the extracted cephalo folder.

### Added

- **Target directory selection** in both setup scripts. After a fresh extraction of cephalo, users can now decide at setup time where the project should be created, instead of working directly inside the download folder.
  - **`setup.sh`**: new `--target PATH` flag. If the flag is omitted and the run is interactive, the script asks: *"Where should the project be created? [1] Here / [2] Choose a different directory"*. On choice 2 it prompts for a path. Tilde expansion (`~/Documents/...`) is supported.
  - **`setup.ps1`**: analogous `-Target` parameter and interactive prompt. Tilde expansion uses `$env:USERPROFILE`.
- When a target is chosen, the cephalo template is **copied** into it (via `tar`-pipe on bash / `Copy-Item` on PowerShell, excluding any `.git`). The script then `cd`s into the target and continues the regular setup flow. At the end, the user is asked whether to delete the original folder — a safety check verifies that the folder still looks like a cephalo template before deleting.
- **Edge cases handled:**
  - Target path does not exist: created (including missing parent directories).
  - Target path is a non-empty directory: interactive confirmation required; non-interactive mode refuses and exits 2.
  - Target path equals current location: falls back to "proceed here" with a note.
  - Target path is an existing file (not a directory): exits 2 with an error.
- **`--help`** text in `setup.sh` updated to document the `--target` flag with examples.

### Changed

- **Setup prologue** now implicitly confirms to the user that the project will be created in the location they chose, reducing the "wait, where are my files?" moment that motivated this release.

### Rationale

The original design assumed users would work inside the extracted cephalo folder. In practice, people extract to Downloads and then ask where their thesis is. The new target flow lets users pick a sensible location (e.g., `~/Documents/Bachelorarbeit_KMU_OSS`) at setup time, without breaking the "agents and project content in the same directory" invariant that Claude Code requires.

## [3.0.0] — 2026-04-21

Initial open-source release of cephalo. Rewrite of an institution-specific, German-language v2 predecessor into an institution-agnostic, English-language form.

### Added

- 10 agent definitions (orchestrator, orchestrator-longform, orchestrator-defense, research, writer, source-verifier, format-verifier, style-resolver, methods, data).
- 8 workflow configurations (seminar, presentation, bachelor flat+longform, master flat+longform, proposal, defense).
- 4 checklists (precheck, format rules, consistency, plagiarism protection).
- 5 templates (status, decisions, handover, feedback log placeholder, styleguide).
- 4 utility scripts (style guide extraction, DOCX post-processing, abbreviations extraction, bibliography check).
- Documentation (QUICKSTART, error catalog, phase separation, long-form structure, multi-project structure, reference management, git introduction).
- Setup scripts for Linux/macOS (`setup.sh`) and Windows (`setup.ps1`).

### Design principles (carried over from v2)

- **Institution-agnostic via `style-resolver`** — citation conventions are extracted from institutional guidelines at setup, not hardcoded in prompts.
- **Phase separation** — content work (Phase A, capable models) and formatting work (Phase B, fast models) run with different agent activation, reducing cost ~60-70% against naive use throughout.
- **Self-contained agents** — Claude Code sub-agents cannot read `CLAUDE.md`, so each agent declares its own file paths and mandatory-read behavior.
- **Structural isolation of guidelines** — the `_guidelines/` underscore prefix keeps institutional rule documents separate from citable source literature.
