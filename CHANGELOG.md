## [Unreleased]

### Changed

- **More of a data script's paths** — the cephalo guard read a path in a script in `data/scripts/` only from the folder the command runs in, so a script that first changes folder (`os.chdir`) and then runs `scripts/01_clean.py` of its data folder was denied as changing cephalo's `scripts/`. In such a script a relative path now counts only if it names a protected path from the command's folder, from the script's own folder and from its data folder alike. The guard also reads more of the paths such a script builds: `Path('scripts', name)`, `Path('.').joinpath('scripts', name)`, `Path.home() / '.claude' / 'settings.json'`, `os.path.join(os.path.expanduser('~'), '.claude', 'settings.json')`, a `.claude/settings.json` joined to any folder, and `rmtree`, `copytree` and `copyfile` imported from `shutil`. A program that opens a file for writing with two levels of brackets in its path, as in `open(os.path.join(a, f(b)), 'w')`, now counts as one that writes a file.

## [1.4.0] — 2026-10-22

**The cephalo guard.** A Claude Code hook, which setup installs, now stops a few slips that the agent definitions forbid but models repeat although they have just read the rule:
- a shell command that writes a file's text,
- a write outside the project,
- `python3` on Windows,
- a redirect in the PowerShell tool,
- a change to the hook settings or `scripts/`,
- an edit of a saved report, after whose Write it asks for the read-back with the file's counts.

A denial names the rule, the definition that holds it and what to do instead. The definitions stay the rule, and a project without the guard works the same. Before the release, reviewers checked the guard against the scope of `SECURITY.md` in five rounds. None found anything critical or high, and the fixes are listed below: it opens no network or device path, stops checking after 5 seconds, keeps its state in a folder of the user's own, and the hook command runs only the project's own guard or that of its multi-project folder. Replayed on every shell command of the second to fourth seminar runs, it stopped only commands that broke a rule. A fourth seminar trial run on Windows went through with the guard on, and a last hook test on Windows gave each of its checks the expected result. The third and fourth runs' other findings are fixed where a definition caused them, among them rule sections read whole, a new source-verifier per round, and the format report read whole with its notes shown. `scripts/verbatim_check.py` now compares the text of Word raw blocks as the export shows it.

### Added

- **The cephalo guard** — a [Claude Code hook](https://code.claude.com/docs/en/hooks) that stops a few slips the agent definitions forbid but models repeat although they have just read the rule; the definitions stay the rule, and a project without the guard works the same. `scripts/cephalo_guard.py` sees the shell, file and agent calls before they run, and a Write after it. It denies a shell command that writes a file's text, such as an inline `py -c` program, a here-document, `echo` into a file, `sed -i`, a PowerShell content cmdlet, or a program saved for it that is not one of cephalo's scripts (S1); a write outside the project folder (S2); `python3 … || py …`, and `python3` on Windows (S3); a redirect in the PowerShell tool (S4); a change to the hook settings or to `scripts/`, which only the user changes (S5, a rule of the guard's own); the main chat's or an orchestrator's Edit of a saved source-verifier report, after whose Write it asks for the read-back with the saved file's counts (R5); and their Write or Edit of a report the format-verifier writes (R6). A denial names the rule, the definition that holds it and what to do instead. Replayed on every shell command the transcripts of the second and third seminar runs show (42 of them only in part), the guard stopped only commands that broke a rule of the definitions: `python3` on Windows, `python3 … || py …` and two `py -c` programs that rewrote files. P1, which looks for a phrase in a task prompt that narrows a check, is off unless switched on: replayed on the third run's seventeen task prompts (four of them cut off in the transcript), it let the three narrowing ones pass and stopped four others, three of them wrongly. `templates/claude_settings.json` holds the hook command, which runs `scripts/cephalo_guard.sh`: it starts the guard with `py` on Windows and `python3` elsewhere, skips the placeholder `python3` of a Mac without the Command Line Tools, and lets every call pass without Python; each hook has `"onFailure": "continue"`, so that a hook that cannot run, as on Windows without Git Bash, never blocks a call (Claude Code 2.1.295 or later; 2.1.283 runs the hooks with the key in place). In a short test on Windows (Claude Code 2.1.283, Git Bash) with an earlier form of the hook, which started an earlier version of the guard without `scripts/cephalo_guard.sh`, it denied Bash and PowerShell calls, a probe hook saw which subagent made a call, and the one timed check took 0.28 s; CI runs the shipped hook command under Git Bash. A last hook test on Windows before the release (Claude Code 2.1.308, Git Bash), with the release's hook command and guard, gave each of its checks the expected result: S1 for a `py -c` program in the Bash tool and for `Set-Content` in the PowerShell tool, S1 and S2 for a write outside the project, S5 for the switch written into `.claude/settings.local.json`, no denial with the switch set, R5's read-back after the Write of a report, which Claude then did, and a subagent's calls seen with its agent type; Claude followed each denial, going on with the tool the message named or stopping to say why. `CEPHALO_GUARD_OFF` (`all`, or a list of rules) and `CEPHALO_GUARD_ON=P1`, set in `.claude/settings.local.json`, switch rules off and P1 on (`docs/scripts.md`, "cephalo guard"). Setup (`setup.sh` and `setup.ps1`) copies the template to `.claude/settings.json` where it is missing, in a multi-project setup also into each sub-project, which Claude Code opens as a project of its own; it keeps a file the user has, and names one that does not run the guard in its "Next steps", with the template to merge by hand. Setup run with `--target` on a project set up with an earlier version, which updates its framework files, installs the guard there too. CI runs the guard's tests on Python 3.9 and 3.13, checks that each of its answers in them, and what the hook prints, has one of four exact shapes (a deny, a note to Claude, a block after a Write, a note to the user), so that no change can make it allow or alter a call unnoticed, checks that every command the definitions, workflows and docs give passes it and that every definition and section its messages name exists, and runs the hook command under dash, the bash 3.2 of macOS and Git Bash. `CLAUDE.md` describes the guard in a section of its own ("Mechanical guardrails"), the FAQ of `README.md` and of the setup assistant explains its message, and `SECURITY.md` names it in its scope.
- **The guard after a security review** — before the release, reviewers checked the guard, its hook command and its setup against the scope of `SECURITY.md`, each finding reproduced or refuted by a second reviewer; none was critical or high. Fixed:
  - **No network or device paths** — the guard runs before Claude Code's permission prompt and reads the scripts, patches and inputs a command names, to check them. A path on a network share (`\\server\share\x.py`, `//server/…`, a WebDAV address) made it contact that server, which on Windows sends the user's sign-in, also when the user then declines the call; a device name such as `COM1`, a device file under `/dev` or a pseudo-file such as `/proc/kmsg` could make it wait or act. It now judges such a path by its name only and never opens it, and the call goes on to Claude Code's prompt as before; a project that lies on a share, or under `/dev/shm`, is still checked. A share reached through a drive letter or a mount point looks like a local folder to it.
  - **A bounded check** — some commands kept the guard busy past the hook's 10-second timeout, after which Claude Code lets the call go on unchecked: a `python3 -c` program or a script in `_scratch/` with a few thousand strings, such as a stop-word list that it writes to a CSV file, took 4 to 35 seconds, and crafted commands (a script that runs itself, a long `find -name` pattern, a planted FIFO in place of a state file or a saved report) longer, or forever. The guard now reads each script once per call, scans a program's strings in one pass, checks nested `{ }` groups without a scan of each, and stops after 5 seconds or 2 MiB of scripts read, letting a call it could not finish checking pass with its note; it reads only regular files, never waiting on a FIFO or a device. On Linux the measured cases now take at most two seconds, the ordinary ones at most half a second.
  - **Umlauts in folder names on a Mac** — a folder named in Finder stores an umlaut as a letter plus a combining mark, while Claude types the precomposed letter; the guard compared the two forms as different text, so in a project folder whose name has an umlaut it would have denied every write into the project as one outside it, and missed a change to `scripts/` named in the other form. On macOS, which treats both forms as one name, the guard now compares paths in one form; on Linux and Windows, which keep them apart, nothing changes. Not yet run on a Mac.
  - **Its own folder for its state** — the guard kept its small state files in `cephalo-guard/` in the shared temporary folder; on a Linux machine with several users, another user could create that folder first and put links in it, through which the guard would have appended a line to a file of the victim's, or created one. The folder is now `cephalo-guard-<user id>/`, made so that only its user can write it, and the guard uses it only when it is that; it follows no link to a state file. On Windows, where the temporary folder is the user's own, the folder keeps its name.
  - **`data/scripts/` inside the project only** — the guard let any script pass whose path contained `/data/scripts/`, also one under `_scratch/` or outside the project, and checked none of them for S5: a program that S1 had denied, saved again as `_scratch/data/scripts/fix.py`, passed, even one that switched the guard off. It now trusts a script in a `data/scripts/` folder of the project only (`workspace/data/scripts/`, `05_Empirical/data/scripts/`), lets it write files as before, and still denies its change to the hook settings or `scripts/` (S5): only a path it names counts (a string with a slash or backslash in it, a path `os.path.join` or `Path` builds from strings, also with a name after them, as in `os.path.join('scripts', name)`, or a string a `shutil` or `os` call takes as the path it removes, moves or copies to, as in `shutil.rmtree('scripts')`), also in a Python program in one of its shell scripts, so that column names, separators and folder names in an analysis script do not; a program fed to Python from another file is checked as that file. It reads a script's strings in one pass, so that a long line of escaped quotes or spaces cannot keep it busy. `docs/scripts.md` names both, and says which shell ways S5 covers.
  - **`~/.claude` for the main chat** — S2 let every agent write anywhere in Claude Code's `~/.claude` folder, so that a research-agent steered by a source document could have put a global `CLAUDE.md`, an agent or a skill there, which would act in every project; the docs did not name the exception. The main chat and an orchestrator still write there (plans, memory, a global `CLAUDE.md` the user asks for); another agent now may write only in the agents' memory folder, `~/.claude/agent-memory/`. The S2 row of `docs/scripts.md` says so.
  - **The hook command stays in the project** — when a project had no `scripts/cephalo_guard.sh` of its own, the hook command ran the one in the folder above it, which is meant for the sub-projects of a multi-project setup; for a project in the Downloads folder or on a shared drive that could have been anyone's script, which then saw every tool call and could even have answered in place of Claude Code's permission prompt. It now does so only in a multi-project setup, where the folder above holds `00_Shared_Materials/`; and without `CLAUDE_PROJECT_DIR`, which Claude Code sets for every hook, it runs nothing instead of looking in the current folder. This closes the case of an unrelated folder above the project; someone who may write that folder can still put both there, so a project keeps its own `scripts/`.
  - **Setup and an odd settings entry** — when `.claude/settings.json` was a link that points nowhere, both setups stopped with an error; when it was a folder, `setup.sh` copied the template into it and reported the settings as installed. Both now keep such an entry, never copy into it, and name it in "Next steps" as one that does not run the guard. CI checks both setups with PowerShell 7 on Linux; the change to `setup.ps1` has not yet run on Windows.
  - **What the docs promise** — `requirements.txt` said that pypdf 6.0 or later keeps a crafted PDF from exhausting memory; it limits how far one compressed stream may expand, but a crafted PDF can still make a run slow or memory-hungry, and the comment now says so and asks to keep pypdf current. `docs/scripts.md` says that on Windows without Git Bash the guard does not run at all, from which Claude Code version `onFailure` applies, and that Claude Code runs a project's hooks only once its folder is trusted.
  - **Text in a Word raw block is compared** — `scripts/verbatim_check.py` left a raw block for the export (`` ```{=openxml} ``) out entirely, but the export writes the text of its `<w:t>` elements into the document, so a sentence copied from a source and put there was neither counted nor compared. That text is now compared with the sources, a paragraph at a time and as Word shows it (a word split over two runs is one word, a tab or line break between runs a space, a text box's paragraphs are paragraphs of their own), and still not counted for the page budget. A raw paragraph in Pandoc's block-quote style (`BlockText`) is a quote, as in the export, where a style its reference document lacks is plain text (a quote style a `--base` template adds, such as `Zitat`, is compared as plain text too); one in the bibliography is an entry of it: it stays out if every entry has a year, and otherwise the whole section is compared, as in the export. A raw block inside an HTML comment, a `{=docx}` block, which Pandoc drops, and the bookmark above the reference list, which has no text, stay out. CI checks these cases.

Before, no definition said how; in a Windows trial run each round of answers cost a new style-resolver run, and ten blocking questions, eight of them on rules a literature review without figures never needs, took two rounds before the first extract.
- **style-resolver** — an open rule has `❓` as its value wherever it appears; one of its competing readings must not stand as a value in another rule. In a Windows trial run the block-quote rule read "from 40 words" while the threshold itself was marked contradictory.
- **Extract verification** — the source-verifier's verdict on an extract covers its quotes, page numbers, term lists, secondary-citation flags and bibliographic data; remarks on the extract's own wording (core claims, labels) come as notes with the ✅ and are applied once by the research-agent, without a new round. Only a ✅ sets `verified`; an extract that reaches the loop limit without one stays `draft`, and the orchestrator asks the user. In a Windows trial run, 47 of 47 quotes and page numbers were correct on the first pass, yet seven wording notes started three more rounds (five agent runs, more than half of the session's cost), and the last extract was set to `verified` without a final ✅.
- **Orchestrators** — record each returned agent call in the state file (`workspace/state.md`, long-form `00_Status.md`) before the next call, not only at the end of a chapter or chat; the flat orchestrator also creates `workspace/state.md` at Step 0, which setup does not. In a Windows trial run the session ended at a usage limit with three new extracts the state file did not know.
- **Orchestrators** — two new principles: a task prompt names the definition, `styleguide.md` or checklist that holds a rule instead of paraphrasing it, and nothing is written outside the project folder, scratch copies included. In a Windows trial run the orchestrator's paraphrase assigned citation notation to `[content]`, against the style-resolver's own rule, and it left three copies of the extracts in the system's temporary folder.
- **`checklists/precheck.md`** — inspecting a file in the pre-check means `file` and a look at its first page; the research-agent and the style-resolver read sources and guidelines in full later. In a Windows trial run the orchestrator read every PDF in full during the pre-check, on the session's main model.
- **Citekeys only where they can be rendered** — the writer-agent writes Pandoc citekeys only when the decision log says the project renders them (a `literature.bib` plus Pandoc and a CSL file that matches the styleguide's citation style; a new item in section 6 of `checklists/precheck.md`), otherwise citations in the styleguide's format. It also gets the citekey forms for a prefix such as `vgl.`, a German locator and a secondary citation; `docs/reference_management.md` describes the case without a matching CSL file. Before, a `literature.bib` alone switched to citekeys: in a Windows trial run without Pandoc and without a CSL for the guideline, the chapter never showed a citation in the styleguide's form.
- **Status symbols** — the source-verifier, format-verifier, style-resolver and research-agent definitions say that ✅ ⚠️ ❌ 🟡 ❓ are status codes the other agents and the workflow criteria search for, to be written as these characters even where an agent would otherwise avoid emojis. In a Windows trial run two source-verifier runs wrote `[OK]`, `[WARN]` and `[ERROR]` instead, citing a request to avoid emojis that the orchestrator had not made.
- **source-verifier** — a term the source does not use for a concept, in particular one on the extract's "Terms NOT in source" list, is an error (❌), as the rule "technical terms are sacred" demands; only a grammatical variant of the source's own term stays ⚠️. `checklists/plagiarism_protection.md` (pattern 3) says the same. In a Windows trial run a planted synonym from that list was found but rated as mild as a stylistic "therefore".
- **source-verifier** — a verbatim run that crosses a sentence boundary counts as one run, and wording it suggests as a fix must itself pass the page and plagiarism checks. In a Windows trial run no run reported a seven-word run across a sentence boundary, and one suggested sentence carried an eight-word verbatim run and a wrong page; the writer-agent caught both.
- **research-agent** — at most three "Terms NOT in source" per entry, and "completeness over selection" applies to the passages, not to extra fields in an entry. In a Windows trial run the extracts were accurate (43 of 43 quotes) but listed four to nine negative terms per entry and added fields of their own: nine short pages took nine minutes.
- **`checklists/precheck.md`** — the result line for examination materials has a ⚠️ for gaps (missing recommended documents) next to ❌ for missing required ones, and an unanswered question about such a document stays under open issues. The overall result already knew "⚠️ with gaps"; the line did not.
- **Orchestrators** — save every source-verifier report as a file (flat: `workspace/output/verification/`, long-form: a `verification/` folder in the phase folder), since the verifier cannot write one, and hand it to the agent in a return call together with the files that agent may change. In a Windows trial run the reports of several thousand words existed only in the orchestrator's context; a chat ending before the revision would have lost them, and an overly narrow return prompt kept the writer from updating a "Used in" line.
- **style-resolver** — names in its summary which open entries the course assignment rules out (tables, figures, statistics in a literature review), so the user can close them in one answer; deletes `_styleguide_rawtext/` after reading it if it created the folder itself; and knows that text extraction loses non-breaking spaces, so `in_text.nbsp_before_page` comes from the guideline's prose. All three came up in a Windows trial run.
- **research-agent, source-verifier** — a page number is the one printed on the page, not the PDF viewer's page index (an excerpt or scan often starts at p. 45 on PDF page 1); a page without a printed number is marked ❓. Only e-book pagination was covered before. The agents got it right in both Windows trial runs, but no definition said so.

### Security

- **ZIP extraction is routed through `scripts/extract_styleguide.sh`** in `research-agent.md` and `style-resolver.md`. Both previously instructed a bare `unzip`, bypassing the script's `safe_extract_zip()`, which rejects entries carrying absolute paths or `..` components. A prepared archive — a style guide downloaded from anywhere — could otherwise have written outside the target directory. The agents and `checklists/precheck.md` now also rule out every other extractor (`tar`, `7z`, Python `zipfile`, PowerShell `Expand-Archive`), the research-agent runs the script on a scratch folder with an explicit output folder, and CI guards against a regression.
- **Prompt-injection guardrails** added to all ten agent definitions: source and guideline content is material to quote and summarize, never a directive, and the same holds for the extracts, data files, handovers and agent reports the other agents read. Text inside a PDF, ZIP, or e-book can be written to read like an instruction addressed to the agent; the agents now record such text as a flagged note and continue the original task instead of acting on it. `style-resolver.md` lists it as a labelled "not a rule" open question, never in a rule section of `styleguide.md`; `source-verifier.md` labels it as instruction-like content rather than a citation issue. `SECURITY.md` names this risk, but no agent definition had previously addressed it.
- **`requirements.txt` gained upper bounds** (`python-docx>=1.0.0,<2.0`, `pypdf[crypto]>=6.0.0,<7.0`). An open range would silently pull in a new major release that changes the APIs these scripts rely on. The pypdf floor is 6.0, which caps decompressed stream size: with an older pypdf already installed, pip kept it, and a crafted guideline PDF could exhaust memory.
- **`docs/setup-wizard.html`: PowerShell quoting** — the generated command now also doubles the typographic single quotes U+2018–U+201B, which PowerShell treats as quote characters. A target containing one could end the quoted path and run the rest of the field as PowerShell commands; an ordinary folder name with an autocorrected apostrophe (`O’Brien`) broke the command.
- **`docx_postprocess.sh` refuses documents containing symbolic links.** unzip restores symlink entries, so a crafted `.docx` could make the re-zipped document embed arbitrary local files (e.g. an SSH key) or make the settings patch write outside the work directory. The entries are checked in the archive before unpacking: under Git Bash, unzip turns a link entry into a copy of its target by default, which a check on disk afterwards would miss.
- **`extract_styleguide.sh` caps disguised ZIPs** at 512 MiB unpacked and 10,000 entries ("Blocked (security)"), so a small crafted archive can no longer unpack to more than that (a text member close to the cap is still read into memory whole, which takes several GiB).
- **Personal data in generated projects** — `.gitignore` (and the copy both setup scripts write) now keeps all of `data/raw/` and `data/processed/` out of Git, as the workflows promise, instead of only `*.csv`/`*.xlsx` and `*_personal*`/`*_identified*` names (interview transcripts or SPSS files could be committed); the `data/processed/.gitkeep` placeholder is now actually committed, in multi-project main works too. LibreOffice lock files (`.~lock.*#`, which record user and host name) and Word `~WRL*.tmp` files are ignored too.
- **Setup: no deletion of a project** (release review) — started from a project (set up "Here" earlier) with a new target, both setup scripts offered to delete that folder as "the original cephalo template folder", and the copy leaves out `.git/`: answered with y, the project's whole Git history was gone. A folder with `00_Status.md`, `00_Shared_Materials/`, `workspace/` or `styleguide.md` is now kept, with a note.
- **`docx_postprocess.sh` also refuses links declared in Info-ZIP's ASi extra field** (release review), whose mode unzip applies even when the entry's attributes show none: under Git Bash, unzip writes a copy of the link's target, which the check after unpacking cannot see.
- **Personal data** (release review) — `docs/git_introduction.md` says that a cloud sync of the project uploads `data/raw/` and `data/processed/` despite `.gitignore`, and `data-agent.md` keeps the pseudonymization key out of the repository.
- **CI** runs with a read-only `GITHUB_TOKEN` (`permissions: contents: read`) and a job timeout (15 minutes; 20 for the macOS/Git Bash job).

## [6.2.0] — 2026-04-22

First genuine feature release after the v3→v6.1 hardening series. Users can now choose where their project lives, instead of being forced to work inside the extracted cephalo folder.

### Added

- **Target directory selection** in both setup scripts. After a fresh extraction of cephalo, users can now decide at setup time where the project should be created, instead of working directly inside the download folder.
  - **`setup.sh`**: new `--target PATH` flag. If the flag is omitted and the run is interactive, the script asks: *"Where should the project be created? [1] Here / [2] Choose a different directory"*. On choice 2 it prompts for a path. Tilde expansion (`~/Documents/...`) is supported.

  - Target path does not exist: created (including missing parent directories).
  - Target path is a non-empty directory: interactive confirmation required; non-interactive mode refuses and exits 2.
  - Target path equals current location: falls back to "proceed here" with a note.
  - Target path is an existing file (not a directory): exits 2 with an error.
- **`--help`** text in `setup.sh` updated to document the `--target` flag with examples.

### Changed

- **Setup prologue** now implicitly confirms to the user that the project will be created in the location they chose, reducing the "wait, where are my files?" moment that motivated this release.

### Rationale

The original design assumed users would work inside the extracted cephalo folder. In practice, people extract to Downloads and then ask where their thesis is. The new target flow lets users pick a sensible location (e.g., `~/Documents/Bachelorarbeit_KMU_OSS`) at setup time, without breaking the "agents and project content in the same directory" invariant that Claude Code requires.
