# Pre-check (Step 0)

**Purpose:** Blocking pre-check before any content work.
**Executed by:** Orchestrator (in multi-agent workflows) or user manually (in seminar_2agent and presentation_3agent, which have no orchestrator).
**On missing required materials:** STOP. Inform the user. Do not make assumptions. (A missing recommended document is noted as a gap; see section 1.)

**Applies to:** `seminar_2agent`, `presentation_3agent`, `bachelor_5agent` and `_longform`, `master_7agent` and `_longform`. These workflows all reference this checklist in their Step 0. `proposal_workflow` applies sections 1 and 2 in its Phase 0: it runs before the main work, so no earlier pre-check has covered its materials.

**Does NOT apply to:** `defense_workflow`. It only cites the frozen main work, whose pre-check already covered the materials; its own Step 0 verifies that the styleguide exists and the main work is frozen.

---

## Why a pre-check?

Lessons from past projects: institutional citation guides arrived late, leading to citation conventions only being corrected after dozens of revisions.

The pre-check prevents this by ensuring **before** content work starts that all binding rules and all required sources are available.

---

## 1. Examination materials (citation and formatting rules MUST be present)

These documents define the rules the work must follow. The citation guide and the formatting guidelines are required (if the institution has none, the published standard adopted instead, logged as a decision). The other three are recommended: if one is missing, ask the user whether the institution provides it, list it as a gap in the pre-check result (⚠️ with gaps), and continue.

- [ ] **Course assignment** — describes topic, scope, formal requirements (recommended)
- [ ] **Examination guide** — assessment criteria, structure of the work (recommended)
- [ ] **Citation guide** — verify version is current (versions differ) (required)
- [ ] **Formatting guidelines** — layout requirements (required)
- [ ] **Plagiarism prevention guide** — institution-specific definition (recommended)

**Storage location:**
- Flat structure: `workspace/sources/_guidelines/`
- Long-form: `guidelines/` at project root
- Multi-project: `00_Shared_Materials/guidelines/`

---

## 2. Sources (MUST be present per chapter)

For the active chapter, all sources to be cited must be available.

- [ ] All relevant sources available as files the agents can read: PDF (also scanned print) or plain text
- [ ] E-books (EPUB) converted first: an EPUB is a ZIP archive the agents cannot open. Convert it to PDF or text (e.g. with Calibre) and cite the print edition's page numbers where the e-book shows them; if it has none, ask how to cite it (chapter or section) and log the answer as a decision (`00_Decisions.md`; flat projects: `workspace/state.md`)
- [ ] Access verified (institutional databases — sessions still valid?)
- [ ] No source from memory only — original file must exist
- [ ] File contents inspected; do not trust filenames. `file` and a look at the first page (title, author, page numbering) are enough here: reading a source in full is the research-agent's job in its chapter step, and the style-resolver reads the guidelines when it runs

### File disguise check

Some institutional course files are ZIP archives with JPEGs/TXTs disguised as `.pdf`.

```bash
file source.pdf
# "PDF document"        -> real PDF, pdftotext works
# "Zip archive data"    -> NOT a real PDF: extract only with scripts/extract_styleguide.sh
#                          (see research-agent), never with unzip or another extractor
```

Filenames can be misleading: a file named with the topic might actually contain a different chapter or even a different work. Always verify content.

### Page-number integrity

- [ ] For e-books: use print edition page numbers, not e-book pagination
- [ ] For scans: page numbers legible in the scan?
- [ ] For multi-language editions: correct edition selected?

---

## 3. Project files (from second chapter onward)

- [ ] State file with status of the previous chapter present
- [ ] Feedback file (if it exists) up to date
- [ ] Current Word document / PPTX (latest version) available, once one exists (thesis and seminar chapters are drafted in Markdown; the DOCX is exported for the formatting phase)
- [ ] Long-form: `00_Status.md` current
- [ ] Long-form: most recent `handover.md` of the active phase present (first chat of a new phase: none yet; the orchestrator creates it from `templates/handover.md`)

---

## 4. Styleguide status (after style resolution)

Step 0 runs before the style-resolver (Step 0.5), so on a new project `styleguide.md` does not exist yet: check this section once Step 0.5 has run, and at every later chapter start.

- [ ] `styleguide.md` has been generated by the style-resolver
- [ ] No open `[content]` entry under "Open questions" in `styleguide.md` (an entry without a tag counts as `[content]`) — required before any chapter is drafted
- [ ] No open `[format]` entry — required before the formatting phase (Phase B; in workflows without one, before the formatting check named in the workflow)
- [ ] Citation guide version noted in `styleguide.md`

**On open `❓` entries:** with an open `[content]` entry, do not draft chapters; with an open `[format]` entry, do not begin formatting work. First obtain clarification from the supervisor, then record the answers in `styleguide.md` as `.claude/agents/style-resolver.md` describes ("Recording answers to open questions"), then continue.

---

## 5. Optional checks (recommended)

- [ ] **Citation guide version current?** — check date in the document. Institutions periodically publish updates.
- [ ] **Formatting guidelines version current?**
- [ ] **Course version correct?** — older versions of the same course may have different requirements
- [ ] **Appendix materials** — for empirical work: ethics approval, data protection plan, consent forms
- [ ] **Reference manager** — for > 15 sources: dedicated collection created, auto-export to `literature.bib`

---

## 6. Technical checks

- [ ] **Git repo exists** (long-form / multi-project): `git status` works
- [ ] **Git LFS active** (long-form / multi-project): `git lfs install` was run
- [ ] **Build tools available** (if using scripts):
  - `python3` (≥ 3.9) — required for all utility scripts
  - `pip install -r requirements.txt` — installs `python-docx` and `pypdf` (with `cryptography` for AES-encrypted PDFs)
  - `pandoc` — optional, for DOCX → plain-text conversion
  - `pdftotext` (poppler-utils) — optional fallback in `scripts/extract_styleguide.sh` (the script prefers Python-based extraction via `pypdf`)
  - `unzip` plus a working Python 3 — required by `scripts/docx_postprocess.sh`. Git Bash on Windows ships with `unzip` by default; re-zipping is done with Python's `zipfile` module, so `zip` itself is never invoked. See `docs/scripts.md` for details.
- [ ] **Citation rendering decided** (only with a `literature.bib`): citekeys in the chapters (`[@key, S. 5]`) turn into citations in the styleguide's form only through Pandoc with a CSL file that matches the styleguide's citation style (`docs/reference_management.md`, "Citation processor pipeline"). If both are available, record "citations as citekeys" in the decision log (`00_Decisions.md`; flat: `workspace/state.md`); otherwise the writer writes citations in the styleguide's format directly. Ask the user when unsure.

---

## 7. On missing materials

### Procedure

1. **STOP** — no content work begins
2. **Inform the user** with an exact list:
   ```
   The following materials are missing:
   - [list of missing documents]
   
   The following sources are not accessible:
   - [list of inaccessible sources]
   
   The following ❓ [content] items in styleguide.md are open:
   - [list of open items]
   ```
3. **Suggest concrete next steps** (upload, supervisor clarification, etc.)
4. **Resume only after** all items are addressed (a missing recommended document from section 1 is a gap, not a block)

### Do NOT

- Make assumptions about what is "probably" meant
- Work with sources mentioned only by filename (not actually read)
- Guess the styleguide

---

## 8. Output of the pre-check

The orchestrator (or user) documents the result in the state file:

```markdown
## Pre-check result

**Performed:** [date]
**Result:** ✅ complete / ⚠️ with gaps / ❌ blocked

**Examination materials:** ✅ / ❌ [list of missing items]
**Sources:** ✅ / ❌ [list of missing items]
**Styleguide:** ✅ / ❓ [open items: N content, M format]
**Technical tools:** ✅ / ❌ [list of missing items]

**Decision:**
- Work can proceed ✅
- Work paused until the blocking gaps are closed ❌
```
